## 3. 踩过的坑（写进记录，避免下次重犯）

1. **`srun` 会吞掉 stdin**：用 `ssh hepnode 'bash -s' < script` 跑探测脚本时，
   脚本里第一个 `srun` 会消费掉后面的脚本内容，导致 `st: unbound variable` 之类的诡异错误。
   → 正确做法：`scp` 上去再 `bash /path/script.sh`。
2. **只看 `srun` 的 waiting 提示会误判并发**：第二个作业会先打印 `queued and waiting for resources`，
   等第一个结束后才打印 `has been allocated resources`，看起来像「并发成功」。
   → 必须用 `squeue` 看 `STATE/REASON`，或 `scontrol show node` 看 `AllocTRES`。
   我第一次复核就因此误判「一节点一作业已修复」，第二次用 `squeue` 才纠正。
3. **`sbatch -n 16 -c 16`** 是 256 核请求，会被拒绝（`Requested node configuration is not available`），
   要写 `-n 1 -c 16`。
4. **`set -u` + 未定义的 `LD_LIBRARY_PATH`** 会直接终止脚本（v4 就是这么丢掉了后半段输出）。
   探测脚本里一律用 `${VAR:-}`。

## 4. 对后续工作的影响

- 作业模板不变：**不写 `--mem`、必加 `--hint=nomultithread`、batch 里显式 `OMP_NUM_THREADS=16`**。
  已同步到本仓库 `scripts/bench.slurm` / `scripts/profile.slurm`。
- 集群上 **没有 FFTW/OpenBLAS**：V1 的 FFT 要么 vendored pocketfft，要么自带源码编译到 `~/opt`，要么自己写。
- **BLAS 的临时退路**（只用于对照实验，不能进提交）：`~/venv` 里 scipy 自带 OpenBLAS，
  `~/venv/lib/python3.14/site-packages/scipy.libs/libscipy_openblas-5f890258.so` 导出了 `cblas_sgemm`。
  但本题 Mel 投影极稀疏（~4096 taps/帧 vs 稠密 1M），**根本不需要 BLAS**。
- **perf 不可用**：只能靠程序内 `std::chrono` 分阶段计时 + A/B 对比（§4.5 已记）。
- 集群 Python 无 numpy：`validate.py` 必须用 `~/venv/bin/python` 跑（`scripts/bench.slurm` 已自动探测）。
