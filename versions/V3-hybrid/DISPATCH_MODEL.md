# 调度模型（DISPATCH_MODEL）

## 1. 目标

每次调用 `compute_melspectrogram()` 都是**一个独立进程内的一次完整计算**，
因此比较对象是端到端整程耗时：

```text
进程启动 + PCM 读入 + int16→float 转换 + FFT + Mel 滤波 + 功率恢复
        + 输出写盘 (+ CUDA 上下文/cuFFT/显存/传输)
```

CUDA 的固定成本（驱动上下文、cuFFT plan、显存分配、H2D/D2H）在单次调用里必须全部摊销，
这正是小输入应该留在 CPU 的原因；而大输入 CUDA 的吞吐优势才会超过这笔固定成本。
调度模型就是这两条成本曲线的交点。

## 2. 输入特征

模型只使用三个由调用参数即可算出的工作量量，与用例名、文件名、音频内容、
测试集特征完全无关：

```text
samples = |y|                                   # 输入样本数（int16 单声道）
frames  = 1 + (samples - n_fft) / hop_length    # 与后端完全一致的帧数

work    = frames * n_fft * log2(n_fft) / 1e8    # FFT 体量（浮点运算量代理）
input   = samples * 2 / 1e6                     # 输入载荷 MB（读入 + 转换 + H2D）
output  = n_mels * frames * 4 / 1e6             # 输出载荷 MB（功率恢复 + 写盘 / D2H）
```

`f_min` / `f_max` 不进入模型：H1 的 10 个频带点（同 `n_fft`、同帧数，覆盖
0–22.05k、300–8k、0–48k 等）实测差异 ≤ 5%，落在测量噪声内，被既有项吸收。
`sr` 不直接影响成本，只通过 `frames` 间接体现。

## 3. 模型形式

每条后端一条线性模型，NNLS 拟合，系数非负 ⇒ 预测对工作量单调不减：

```text
T_cpu  = 0.037173 + 0.0016168*work + 0.0      *input + 0.0027815*output
T_cuda = 0.245811 + 8.7131e-05*work + 0.0036889*input + 0.0021713*output
```

| 系数 | CPU | CUDA | 物理含义 |
|---|---|---|---|
| 常数项 (s) | 0.0372 | 0.2458 | 每进程固定成本：进程启动/解码/滤波库 vs CUDA 上下文 + cuFFT plan + 显存 + 首传 |
| `work` (s/单位) | 1.6168e-03 | 8.7131e-05 | FFT 吞吐：L40 约为 16 vCPU AVX-512 的 18.6 倍 |
| `input` (s/MB) | 0（被吸收） | 3.6889e-03 | H2D + 转换；CPU 侧读入/转换相对 FFT 很小，NNLS 归零 |
| `output` (s/MB) | 2.7815e-03 | 2.1713e-03 | 功率恢复 + 写盘 vs D2H + resize + 写盘 |

判据是最朴素的 argmin，没有经验阈值、没有 hysteresis、没有按用例分流：

```cpp
cuda  if  T_cuda(work, input, output) < T_cpu(work, input, output)
```

## 4. 拟合数据

- 作业：Slurm `hybrid-h2`/H1 Job 375，节点 hepnode3，单节点 1×L40（46068 MiB，
  driver 595.91.07），16 vCPU cpuset `0-3,16-19,32-35,48-51`（Xeon Gold 6338），
  CUDA 13.4.92，g++ 15.2.0。
- 38 个测量点：官方 4 组 + 合成矩阵（`frames` 1…192397、`n_fft` 256…16384、
  `n_mels` 8…256、10 组频带、4 个大型点）。
- 每点 CPU/GPU 交替执行、顺序逐轮翻转，3 轮，取中位数；全部点 CPU/CUDA
  输出均通过校验（官方点对 `data/` 期望输出，合成点 CPU vs CUDA）。
- 拟合：`scipy.optimize.nnls`，`scripts/fit_hybrid_model.py`；
  GPU 侧 MAE 9.5 ms，CPU 侧 MAE 27 ms（小任务上 CPU 常数项偏保守）。
- H2（Job 397）的 38 个点**不参与拟合**，作为留出验证使用（见 6.2 节）。

## 5. 交叉点

把特征按 `frames` 展开，交点有闭式解。下表是 `hop=128`、`sr=96k`、
`n_mels=256` 时的预测交点，以及实测验证：

| 配置 | 预测交叉点 | 实测验证 |
|---|---|---|
| `n_fft=8192, n_mels=256` | ≈ 159k 帧（≈212 s 音频） | 32.8k 帧 CPU 快 1.65×；192.4k 帧 CUDA 快 5.7% |
| `n_fft=16384, n_mels=256` | ≈ 65k 帧（≈87 s 音频） | 32.8k 帧 CPU 快 1.04×；65.5k 帧 CUDA 快 1.30× |
| `n_fft=8192, n_mels=64` | ≈ 248k 帧 | 192.4k 帧仍 CPU 快 12%（官方 small_mels） |
| `n_fft=4096, n_mels=256` | ≈ 483k 帧 | 该网格内始终 CPU |

解读：

1. **小任务**：`T_cuda` 的 0.246 s 常数项压倒一切。`frames=4096, n_fft=8192`
   实测 CPU 0.051 s vs CUDA 0.254 s（约 5×）。
2. **中任务**：两条线性曲线斜率接近（`n_fft=8192` 时 4.57e-6 vs 3.26e-6 s/帧），
   所以交界处决策对噪声敏感，收益也只有个位数百分比。
3. **大任务**：`n_fft=16384`、≥65k 帧后 CUDA 领先迅速扩大
   （65.5k 帧 1.30×、128k 帧 1.51×、192k 帧 1.40×）。
4. **输出维数**：`n_mels` 同时抬高两侧的输出项，但 CUDA 侧还有输入项，
   所以 `n_mels` 越小越偏向 CPU（small_mels 就是这种情形）。

## 6. 决策质量

### 6.1 训练集（H1，Job 375，38 点，模型就是在这批数据上拟合的）

| 指标 | 数值 |
|---|---|
| 与逐点最优后端一致 | 37/38（97.4%） |
| 留一交叉验证（LOO，重拟合后预测） | 35/38（92.1%） |
| 被判错点的最大代价 | +5.7% |

唯一判错的 `official-default`（`n_fft=8192, 192397 帧, n_mels=256`）实际
CPU 0.849 s / CUDA 0.897 s，相差 5.7%；而**同一配置**在合成矩阵里再测一次得到
CPU 0.981 s / CUDA 0.852 s，CPU 侧本身就有 15% 的进程间波动。
即：该点处在交叉点附近，谁赢是噪声级事件，任何静态线性模型都会在此处翻转。
没有为这一个点加入阈值、margin 或特例：加入 3%–20% 的 margin 反而会在
`frames-192397`、`large-65536` 上稳定判错（margin 扫描原始输出见 `raw/h1/`），
故保留纯 argmin。

### 6.2 留出验证（H2，Job 397，同一模型未重新拟合）

| 指标 | 数值 |
|---|---|
| 与逐点最优一致 | 37/38（97.4%） |
| 唯一判错点 | `official-small_mels`，代价 +21.0% |
| 全矩阵累计 | auto 8.331 s，始终 CPU 10.010 s，始终 CUDA 14.003 s，逐点最优 8.067 s |
| auto 相对逐点最优 | +3.27% |

H2 的这次偏差不是模型结构问题，而是**训练会话的 CPU 恰好处于较快状态**：
同一份 CPU 二进制、同一配置在 H1 测得 0.493 s，在 H2/H2b 测得 0.661–0.716 s
（`BENCHMARK.md` 3.6 节）。模型因此把 `small_mels` 判给 CPU，而当场 CUDA 快 20%。

### 6.3 稳健性：合并两场会话重拟合的对比（未采用，仅记录）

用 H1+H2 共 76 点重新 NNLS：

```text
T_cpu  = 0.035955 + 0.0013810*work + 0.0026310*input + 0.0027140*output
T_cuda = 0.243253 + 3.4690e-05*work + 0.0039421*input + 0.0022694*output
```

| 模型 | H1 上一致/最大代价 | H2 上一致/最大代价 |
|---|---|---|
| 交付模型（H1 拟合） | 37/38，5.7% | 37/38，21.0% |
| 合并重拟合 | 36/38，12.0% | 38/38，0.0% |

两者总量相当：交付模型在 H1 上更准，合并模型在 H2 上更准，且合并模型对两场会话
的样本内误差更小。交付时保留 H1 单会话拟合，原因是它给出了**干净的留出验证**
（H2 完全没有参与训练），代价是交叉区偏乐观；换部署环境时应按第 8 节流程重标定，
而不是沿用任何一份写死的系数。

## 7. 调度器自身开销（实测）

Job 405（同节点、13 个代表点、5 轮交错，`scripts/dispatch_overhead.py`）：

| 对比 | 中位 | 范围 | 结论 |
|---|---:|---:|---|
| `auto` − 统一二进制强制 CPU（CPU 决策点） | +0.75 ms | −0.8 … +41.7 ms | 调度器开销，含决策日志 `fprintf` |
| 统一二进制强制 CPU − CPU-only 二进制 | +4.0 ms | −43 … +78 ms | 携带 CUDA DSO 的启动成本，与后端选择无关 |
| `auto` 无可见设备 − 统一二进制强制 CPU | +3.4 ms | −17 … +89 ms | 失败的设备探测（仅异常环境） |

- 决策是 6 次乘法、6 次加法、1 次 `log2`，无分配、无锁、无线程、无 CUDA 调用。
- 只有**预测为 CUDA** 时才调用 `cuda_backend_available()`（`cudaGetDeviceCount`），
  预测为 CPU 时连设备探测都不做。
- `strace` 验证（`raw/h2/h2-no-cuda-init-397.txt`）：CPU 决策下
  `/dev/nvidia*` 打开次数为 **0**（强制 CUDA 为 46 次）；`libcuda.so` 的 dlopen
  次数 1 vs 3——前者来自进程启动时链接的 `libcudart`，不构建设备上下文。
- 不做试跑，不做“跑一半比一比”，不缓存跨进程状态。

## 8. 硬件能力如何进入决策

模型是“硬件画像”相关的：

- **设备有无**：二进制能力位（是否编入 CUDA）+ `cuda_backend_available()`
  决定 auto 是否允许选 CUDA；不可用时回退 CPU。
- **CPU 侧**：`Makefile` 按 ISA 选择 Batch16/8/1 实现，不同 ISA 的
  `work` 系数不同，必须重标定。
- **GPU 侧**：常数项主要来自驱动/上下文与 cuFFT plan 建立，换卡、换驱动、
  换 CUDA 版本都会变。

因此代码里系数是可覆盖宏：

```c
#define MELSPEC_MODEL_CPU_CONST  0.0371727216
...
```

重标定流程（不改代码逻辑）：

```bash
python scripts/hybrid_bench.py --cpu BIN_CPU --cuda BIN_CUDA --auto BIN_AUTO \
       --runs 3 --out raw/h2/hybrid-h2-<job>.json
python scripts/fit_hybrid_model.py raw/h2/hybrid-h2-<job>.json --emit-cpp
# 把输出的宏写回 src/melspec.cpp（或 -D 传入）后重建
```

## 9. 适用范围与已知局限

- 标定范围：`n_fft` 256–16384，`frames` 1–192397，输入 ≤ 49 MB，输出 ≤ 197 MB。
  超出该范围的线性外推属于估计，需重新标定。
- CPU `input` 系数为 0 是被 NNLS 在该网格上吸收的结果；输入远大于 49 MB
  （例如分钟级 192 kHz 录音）时应重标定，令输入项重新获得权重。
- 模型比较的是“本进程一次性完成”的成本。若将来改为常驻服务、复用 CUDA 上下文
  与 cuFFT plan，`T_cuda` 的常数项会大幅下降，交叉点左移，必须重标定。
- 多进程争用 GPU 时实测 `T_cuda` 会变差；模型不含争用项，此时应以实测数据重标定
  或显式使用 `MELSPEC_BACKEND=cpu`。
- CPU 绝对耗时随节点/时段漂移：同一二进制、同一配置跨作业相差 19%–27%
  （`BENCHMARK.md` 3.6 节），交叉区判断应以当次实测为准。
- 决策准确率：H1（训练）37/38，H2（留出）37/38；留一交叉验证 35/38。
  交叉点附近的正负本身可能落在噪声内，不要据此宣称某个后端“必然更快”。
