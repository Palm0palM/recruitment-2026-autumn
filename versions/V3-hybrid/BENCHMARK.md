# Hybrid Benchmark 报告

所有数字都是**完整进程 wall time**（读取 PCM → 计算 → 写输出），不是 Kernel、
不是 FFT 单段、也不是线程时间之和。计时在同一个 Slurm 作业、同一个节点、
同一份输入上完成；CPU/GPU 严格交错执行并逐轮翻转先后顺序。

原始数据（含每轮原始值、最小值、中位数、正确性）保存在：

```text

versions/V3-hybrid/raw/h1/      H1 38 点交叉点测量（Job 375）
versions/V3-hybrid/raw/h2/      H2 三模式终验（Job 397）+ 本地证据
```

## 1. H0：整合两种冻结实现

### 1.1 三套构建的官方 4/4

同一节点、`validate.py --runs 1`（官方脚本口径）：

三套实现的最大绝对误差与各自冻结版本的既有记录一致（CPU ≤ 1.3e-1，
CUDA ≤ 2.2e-1），没有因为拆分/整合出现精度变化。

### 1.2 Dispatcher 是否引入额外开销（5 轮交错，中位/最小）

被测程序：`frozen` = 冻结 CPU 算法直接编译；`cpu-only` = 拆分后的 CPU-only 构建；
`hybrid-cpu` = 统一二进制强制 CPU；`hybrid-cuda` = 统一二进制强制 CUDA。

| 用例 | frozen | cpu-only | hybrid-cpu | hybrid-cuda |
|---|---:|---:|---:|---:|
| default | 0.844 / 0.839 | 0.854 / 0.850 | 0.848 / 0.844 | 0.885 / 0.878 |
| small_mels | 0.685 / 0.626 | 0.684 / 0.618 | 0.667 / 0.658 | 0.568 / 0.536 |
| large_fft | 1.316 / 1.233 | 1.279 / 1.239 | 1.252 / 1.230 | 0.894 / 0.881 |
| narrow_band | 1.247 / 1.219 | 1.241 / 1.182 | 1.255 / 1.187 | 0.893 / 0.878 |

（每格 `中位 / 最小`，秒；5 次原始值在 `raw/h0/h0-modes-363.txt`。）

结论：

- `hybrid-cpu` 与 `cpu-only`、与 `frozen` 的差异都在 ±5% 的进程间波动内
  （default −0.7%，small_mels −2.6%，large_fft −2.1%，narrow_band +1.1%），
  没有系统性变慢；Dispatcher 只做一次 `getenv` 与一次函数调用。
- 统一二进制在**强制 CPU** 时仍会加载 CUDA/cuFFT 动态库（约 3 ms 量级），
  但仍不初始化设备；CPU-only 构建完全没有该开销，因此单独提供。
- 两个后端各自 4/4 PASS，说明“每次调用只走一个后端、完整写满 output”成立。

### 2.3 观察

1. **小任务完全属于 CPU**：CUDA 每进程固定成本约 0.25 s，而 CPU 在
   `frames=4096, n_fft=8192` 只要 0.05 s（快约 5×）；`frames≤512` 时快 10–20×。
2. **`n_mels` 越大越偏向 CUDA**：`n_mels=8` 时 CPU 0.040 s（CUDA 0.252 s），
   `n_mels=256` 时 CPU 0.051 s，CUDA 输出传输成本随之上升但仍远高于 CPU。
3. **频率范围几乎不影响结论**：同 `n_fft=8192` 的 5 个频带点 CPU 0.049–0.054 s，
   CUDA 0.257–0.262 s，差异 ≤ 2%，被两次相同配置测量间的噪声覆盖
   （例如 `nfft-16384` 0.0769 s 与 `band-16384-0-22050` 0.0855 s 是同一配置的两次测量）。
4. **交叉点在 65k–160k 帧区间**，取决于 `n_fft` 与 `n_mels`；越过交叉点后
   CUDA 领先幅度迅速扩大（65k 帧 1.30×、128k 帧 1.51×）。
5. **CPU 侧进程间波动 5%–25%**（同一配置的两次测量：CPU 0.849 vs 0.981 s），
   因此交叉点附近的“谁更快”本身是噪声级事件；这直接限制了任何静态模型的精度。

### 2.4 成本模型

由上述 38 点用 NNLS 拟合出的两条线性模型（详见 `DISPATCH_MODEL.md`）：

```text
T_cpu  = 0.037173 + 0.0016168 * work + 0.0027815 * output
T_cuda = 0.245811 + 8.7131e-5 * work + 0.0036889 * input + 0.0021713 * output
work = frames*n_fft*log2(n_fft)/1e8,  input = samples*2/1e6,  output = n_mels*frames*4/1e6
```

逐点最优后端命中 37/38（仅 `official-default`，实际差距 5.7%），
留一交叉验证 35/38。模型只用于 H2 的 `auto`，强制模式完全不经过模型。

### 3.5 调度器开销 vs CUDA 动态库加载开销（Job 405，13 个代表点，5 轮交错）

| 指标 | 中位 | 范围 | 含义 |
|---|---:|---:|---|
| `auto` − 统一二进制强制 CPU（仅 CPU 决策点，8 点） | **+0.75 ms** | −0.8 … +41.7 ms | 调度逻辑 + 决策日志；不写日志时更小 |
| 统一二进制强制 CPU − CPU-only 二进制（13 点） | +4.0 ms | −43 … +78 ms | 统一二进制启动时加载 CUDA/cuFFT DSO |
| `auto`（无可见设备，回退 CPU）− 统一二进制强制 CPU | +3.4 ms | −17 … +89 ms | 失败的设备探测（驱动存在但无设备） |
| CPU-only 新构建 − H1 旧构建（同一算法） | +2.4 % | −9.8 … +8.2 % | 构建布局差异，无系统性退化 |

- `dispatcher_ms` 中位 0.75 ms 已包含 `MELSPEC_DISPATCH_LOG` 的 `fprintf`；
  决策本身只有几次乘加与一次 `log2`，不分配、不加锁、不调 CUDA。
- 统一二进制的 4 ms 加载成本属于“同时携带两个后端”的代价，与选哪个后端无关；
  不需要 CUDA 的部署应使用 CPU-only 构建（零 CUDA DSO）。
- 探测失败的成本不是常数（几 ms 到 ~90 ms），只在“驱动存在但设备不可见”的异常环境下出现；
  正常 GPU 节点上 auto 选 CUDA 时只做一次成功的 `cudaGetDeviceCount`。

### 3.6 跨会话 CPU 漂移：为什么 `official-small_mels` 会被判错

同一个 CPU-only 二进制（`539600db…`，H1 使用的构建）在 `official-small_mels`
上的测量：

| 会话 | 节点 | CPU 中位 (s) | CUDA 中位 (s) |
|---|---|---:|---:|
| H1 / Job 375 | hepnode3 | **0.493** | 0.552 |
| H2b / Job 405（同一文件） | hepnode2 | **0.661** | 0.560 |

`official-default` 同二进制：0.849（Job 375）→ 1.049（Job 405），+24%；
而 CUDA 侧同一配置仅 0.897 → 0.927（+3%）。
Job 397 内同一个 CPU-only 二进制、同一配置还测到 0.827 s（`validate.py` 单次）
与 1.050 s（矩阵中位）两种结果，跨度 27%。

结论：CPU 侧绝对耗时受节点/时段/前序负载影响可达 20–30%，CUDA 侧 ≤5%。
在 0.05 s 级别的交叉区，20% 的漂移足以翻转胜负，这正是
`official-small_mels` 在 H2 被判成 CPU（+21% regret）的原因，也说明
“用阈值/margin 硬掰交叉点”没有意义。模型训练集（H1）里的 CPU 恰好处在较快状态，
所以它对 CPU 的预测偏乐观；该偏差已在 `DISPATCH_MODEL.md` 第 6/9 节量化说明。
