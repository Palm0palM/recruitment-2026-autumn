# versions/ —— 优化过程记录

本目录按「一个版本一个目录」记录题目优化过程中的每一次可复现的进展。
它是笔试 PPT 的事实来源：**PPT 里出现的每一个数字，都应该能在这里找到对应的命令、代码状态和原始输出。**

## 记录约定

```
versions/
├── README.md                  ← 本文件：约定 + 总览表
├── V0-baseline/               ← 原始朴素实现（tag: v0-baseline）
│   ├── README.md              ← 结论、环境、结果表、瓶颈分析
│   └── raw/                   ← 原始测量输出（bench/validate/perf 的文本）
├── V1-<一句话优化名>/
│   ├── README.md              ← 做了什么 / 为什么 / 收益 / 正确性 / 复现命令
│   └── raw/
└── ...
```

一个版本目录里必须包含：

1. **代码状态**：已提交时记录 commit/tag；未提交时记录起点 commit、源码 SHA-256 和 diff 统计，不虚构 tag。
2. **做了什么**：改动的关键点（配置、数据结构、并行度、库），以及为什么这样改。
3. **正确性**：四组用例的 `max|err|` 与 `PASS/FAIL`（必须来自官方 `validate.py` 或 `scripts/bench.py` 全量模式）。
4. **性能**：四组用例耗时（3~5 次取最小值）；仅在同平台、同口径有基线时计算相对加速比。
5. **复现命令**：完整可粘贴的命令行（含 slurm 提交方式）。
6. **profile 证据**：perf/火焰图/阶段计时（至少给出热点占比）。
7. **踩坑与结论**：这一版学到的东西、失败的尝试（失败的也要记，PPT 里很值钱）。

## 测量口径（必须统一，否则数字不可比）

- 平台：**七边形集群计算节点**（`slurm` 作业，1 节点 16 核），本地数字仅作趋势参考。
- 计时：`validate.py` 报告的「整体进程 wall time，3 次最小值」（含读 49 MB PCM、写 197 MB 输出）。
- 加速比分母：同一作业内的 `librosa`（`validate.py` 自带）。V0 只有本地数据，不用来除集群耗时。
- 正确性容差：`rtol=1e-3, atol=1e-4`（题目给定）。
- 环境记录：节点名、`nproc`、编译命令、库版本（fftw/openblas/gcc）必须写进每个版本。

## 总览

| 版本 | 关键改动 | default 全量 (s) | 测量平台 | 状态 |
|---|---|---|---|---|
| V0-baseline | 原始朴素实现（逐帧 `complex<double>` FFT + 稠密 Mel 乘） | **1645.2**（27.4 min） | 本地 | 完成（集群按学长要求不跑 baseline） |
| [V1-legacy-port](V1-legacy-port/README.md) | 旧解答迁移：FFT 缓存、半长实数 FFT、稀疏逐帧 Mel、16 线程 | **1.537** | hepnode3 / 16 CPU | 全量 4/4 PASS，vs librosa 12.416×；profile 完成 |
| [V2-simd](V2-simd/README.md) | 自研 radix-4 + 跨帧 AoSoA + 支持裁剪/原位恢复 | **0.864**（交错中位数） | hepnode3 / 16 CPU | 全量 4/4 PASS；同次 FFTW 1.149×，Batch4 回退保留 |

> 口径提醒：
> * 本地 15 GiB 内存机器上 default 全量会因功率谱 6.3 GiB 产生换页；集群节点 1 TB 内存没有这个问题，
>   所以**绝对秒数和相对加速比均不能混用不同平台的数据**。
> * 学长要求 baseline 不要占集群资源（他实测跑一组 >1 小时），集群算力留给 V1 之后；
>   V1 之后先本地 smoke，通过后在集群跑优化版本的全量四组。
